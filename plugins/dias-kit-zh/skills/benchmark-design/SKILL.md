# 用 Gray 的手册做基准设计

一份基准是为一项决策服务的仪器。Gray 以如下论证打开手册："No single metric can measure the performance of computer systems on all applications"（没有任何单一指标能够度量计算机系统在全部应用上的性能），因为性能 "varies enormously from one application domain to another"（从一个应用领域到另一个差异极大）。他的回答是**领域特定基准**：一份刻画某一个问题领域典型应用的合成负载，在使结果可比较的规则下运行。本技能把用户的场景变成这样一份基准，写成另一人能够实现的规范，并对照手册的准则加以审计。

Sawyer 的章节（"Doing Your Own Benchmark"）把每个基准分成**负载规范**（做哪些工作）和**测量规范**（如何运行、计时与评判）。下面每一项决策都属于这二者之一。他的主导规则全程适用："the trade-off between reality and simplicity governs all."（现实与简单之间的权衡支配一切。）每做一次这样的权衡，就在做出它的地方记下来，因为读者只能信任自己看得见的简化。

本技能的价值，在于从*这一场景的*成本驱动因素映射到*具体的*设计选择。泛泛的建议（「用真实的数据」「多跑几次」「测量延迟」）正是失败模式。每个旋钮都有默认值和范围，每个指标都有单位，每条规则都有别人可以执行的检查。

## 文件

- `references/spec-template.md` — 交付物。每份规范都用它的结构；按场景缩放各节，但不要悄悄删掉任何一节。
- `references/design-patterns.md` — 来自经典基准的可复用技术（受控选择率、基数阶梯、偏斜输入、与吞吐绑定的规模、冷/热协议、固定时间指标、校准、计入成本的物理调优……）。在步骤 3 和 4 中，从其索引出发，选用能够回答本场景某一成本驱动因素的少数模式（通常三到六个）。没有场景理由的模式只增加成本，并不增加严谨。
- `references/handbook-principles.md` — 带章节归属和短引文的原则。在 Critique（审查）模式下阅读，或当某项决策需要带出处的论证时阅读。把一个想法归于写下它的那一章的作者（O'Neil、Sawyer、DeWitt……），不要笼统地归于 "Gray"。在规范里，只在手册为一个读者可能争议的决策提供理由时才引用手册；规范写给实现者，不必做成框架巡礼。
- `references/beyond-handbook.md` — 后来的基准（TPC-H、TPC-DS、YCSB、JOB、LDBC、CH-benCHmark），以及 1990 年代规则的现代对应（用每小时成本代替五年价格、开放与封闭负载生成）。在步骤 2 阅读，以及在把指标映射到今天的硬件时阅读。

## 模式

- **Design（设计）。** 用户描述一个场景：执行步骤 0–7，并写出一份规范。
- **Critique（审查）。** 用户带来一份计划、一段脚本，或论文的评测章节：按该计划*的现状*执行步骤 1 和步骤 6。列出发现，每一条绑定一条原则，并分级为*使结论不成立*、*削弱它*或*表面*。然后写出修订后的规范（若计划大体健全，则写一份聚焦的改动清单）。
- **Extend（扩展）。** 已有基准缺少一个性质（偏斜、并发、更新、更大规模）：只对这一增量执行步骤 2–5。把结果称为「派生自 X」，因为一个标准基准在被改过的规则下运行，就不再是那个基准，不得借用它的名字。

## 步骤 0 — 采集：收集驱动设计的事实

从对话、仓库（代码、模式、查询日志、数据样本、早先的实验）和用户自己的话里提取这些事实。每一条事实驱动一项点名的设计决策；这就是收集它的原因。

| 事实 | 它驱动的决策 |
| --- | --- |
| 结果将支撑的决策，以及谁来读这些结果 | Gray 的用途类别（步骤 1）、主指标、哪些保持固定 |
| 所比较的系统或变体；哪些固定，以及每个实现者可以自选什么 | 可移植性与公平性规则（步骤 5） |
| 典型操作，及其频率或速率，以及数据访问模式 | 操作集合与配比（步骤 3a） |
| 驱动代价的数据性质：大小、基数、偏斜、相关、局部性、时间结构、更新速率 | 生成器旋钮（步骤 3b） |
| 服务目标：延迟阈值*与*分位数，或一个批处理截止时间 | 主指标上的约束（步骤 4a） |
| 并发：客户端数 × 每客户端速率、思考时间 | 驱动端设计与测试（步骤 3d） |
| 规模范围：所关心的最小与最大数据和硬件 | 规模规则与规模点（步骤 3e） |
| 基准自身的预算，以及可以放弃什么 | 简化（权衡日志） |

若一条缺失的事实会实质地改变设计，就问一次，合并来问。若用户不在，或该事实是一项判断，就假定一个值，说明是假定的，并把它列在规范的*假设*之下，以便日后改正。来自用户数据的实测数字优于猜测；若有数据样本，就计数那些驱动代价的性质（每个键的行数、偏斜、间隙），并引用这些计数。

## 步骤 1 — 框定：你想知道什么？

Sawyer 从三个问题开始，并全程重新检验：*你想知道什么？你准备投入多少？你准备放弃什么？* 在规范的第一节回答它们。

然后点名该基准服务于 Gray 的四种用途中的哪一种，因为每一种固定不同的一组变量：

1. 不同系统在不同硬件上（整系统比较）。
2. 同一硬件上的不同软件（引擎对引擎）。
3. 同一软件跨越一族机器（硬件扩展）。
4. 一个产品的相继版本（回归；在研究中还包括：一项优化打开与关闭，即一次消融）。

陈述本基准必须能够*反驳*的主张（「引擎 A 在每个规模点上、在 p99 ≤ 50 ms 的约束下，维持比 B 更高的吞吐」），以及它*不会*告诉你什么。Sawyer 把未来性能列在基准无法预测的事物之中；Gray 指出，手册的指标不度量易用性、编程或运维。

## 步骤 2 — 先复用，再发明

基准的可信度来自被接受：Gray 把一个基准收入手册的主要准则，是它是否在其领域特定的社区内被广泛接受。把采集到的典型操作和数据性质与已有基准比较（`references/beyond-handbook.md`）：

- **原样即 relevant** → 使用它，遵守它的规则，并说明为何契合。
- **只差一个性质才 relevant** → 扩展它（Extend 模式），并点名所缺的性质。
- **并不 relevant** → 新建一个，并说明已有基准漏掉了哪些典型操作或数据性质。手册自己的新基准就是这样论证的：O'Neil 建立 Set Query，是因为事务基准没有覆盖集合查询；Cattell 建立 Engineering Database Benchmark，是因为 TPC 和 Wisconsin 都不度量来自客户端程序的细粒度导航。

定制基准仍可以借用某个标准基准的生成器、模式或查询，以获得可移植性；说明借用了什么。

## 步骤 3 — 负载规范

**3a. 操作及其精确语义。** 从领域的问题导出操作，而不是从被测系统恰好擅长做什么导出；TPC-D 是 "Designed with business questions built first, followed by SQL."（先建立业务问题，然后才是 SQL。）对每个操作给出它的目的、它的精确定义（查询文本或操作语义）、它的参数，以及它在配比中的份额。

在任何东西被计时之前，就把语义钉死到边界情形上，因为在某个边界情形上不一致的两个系统是在做不同的工作，较快的那个可能只不过是错了。列出该领域具有的每一个边界情形——并列、边界是否包含、NULL 与缺失值、重复、空输入、排序、类型精度——陈述所要求的结果，并让生成器埋入每一种的实例以及期望输出。对时间相关的负载，把迟到和乱序数据（一个事件的摄入时间晚于查询所针对的那个时间）当作一等变体，不要写成脚注：它既改变正确性，也改变代价。

然后按 Sawyer 的方式缩小这个集合：把有若干代码路径的操作拆成加权路径，按速率 × 数据访问模式列表（每张表的随机读 / 更新 / 顺序取），合并模式重合的操作，保留数据访问，丢掉应用逻辑。明确注明不频繁的操作；稀有操作的长尾给缓存带来的压力，是少数热点不会带来的。

**3b. 数据与生成器。** 优先使用带种子的、确定的生成器，使每个系统装入*相同*的数据（TPC-D）。给采集中每一个驱动代价的性质各自一个旋钮，带默认值和范围，并使用 `references/design-patterns.md` 中的模式：选择率受控的列（Wisconsin）、基数阶梯（Set Query）、偏斜或非均匀的输入（TPC-C、AS3AP）、访问局部性（Engineering Database Benchmark）、时间相关负载的时间结构。有意地决定用均匀还是偏斜：TPC-D 选择均匀值，"solely to enhance benchmark reproducibility"（仅仅为了增强基准的可复现性），并承担已知的真实性代价；把这类选择记下来。随生成器附上检查（行数、开头若干行、测得的偏斜），使实现者能够确认自己生成了正确的数据。

**3c. 输入参数。** 在运行时从一个写明的分布中抽取查询参数，使重复执行触及不同的数据，而工作量等价。这使结果缓存失效，并模拟即席使用（TPC-D 的输入变量；Engineering Database Benchmark 的每次迭代中全新的随机零件）。

**3d. 配比、并发与测试。** 把并发写成*客户端数 × 每客户端速率*，不要只写成一个合计速率：Sawyer 的例子是，十个进程、每个每秒一个事务，其行为不同于一千个用户、每个每秒 0.01 个事务。写明思考时间（或写明没有）。当领域有并发用户时，单流测试和多流测试都要包括：因为 TPC-D 把多用户测试做成可选项，大多数已发表的结果，用 Ballinger 所引 Richard Winter 的话来说，"say nothing about the ability of the database engine to deal efficiently with multiple concurrent users"（对数据库引擎高效应对多个并发用户的能力毫无说明）。若领域在读取数据的同时更新数据，就把更新与读并发运行，并加一个把两种效应分开的对照：一组读操作落在写永远不会触及的数据上（历史分区、冻结的表），在有写负载和没有写负载两种情况下测量。没有这个对照，「在写之下更慢」就把干扰，和读仅仅看到了更多或不同的数据，混在一起。

**3e. 规模规则。** 一个规模因子应当决定每一个大小，使读者能够预测任意规模上的工作量。选择适合该领域的规则（见设计模式）：数据库大小绑定于所声称的吞吐（TPC-A/C，因此不能在一个玩具数据库上声称高速率）；固定的合法规模点，只在相同规模上比较，并且均匀增长，使工作量可预测地增长（TPC-D）；相对于缓存容量的大小（Engineering Database Benchmark）；或者一个固定时间的指标，报告在截止时间内处理完的最大规模（AS3AP）。明确规划规模实验：sizeup（更多数据、同样硬件）、speedup（同样数据、更多硬件）、scaleup（两者一起增长），以及系统不再能完成之处的失效点。一项关于扩展的主张，需要足够多的点，才能拟合其趋势并给出不确定度估计；两个点可以拟合任何曲线，而最小的那个点常常被固定开销主导。

## 步骤 4 — 测量规范

**4a. 指标。** 主指标是单位时间内的有用工作，*服从一条响应时间约束*（TPC：在某个写明的分位数保持于阈值之下的同时的吞吐），Gray 把它与**性价比**配对。把价格翻译到本场景：硬件或云实例的每小时成本、核、内存、能耗（见 `references/beyond-handbook.md`）。报告按操作的结果，不要只报告一个复合数；若定义复合指标，给出它的公式和它的病态（TPC-D 的几何平均奖励削短那些短查询，因此需要一条下限规则）。加上使调优代价可见的次要指标：装载与准备时间、相对于原始数据的存储（TPC-D 的磁盘存储比）。

**4b. 响应时间。** 用分位数，不用均值：Sawyer 给出两个平均相同、第 90 百分位却很不同的分布，并建议用第 90 百分位。按服务目标选取分位数。定义**测量点**，即时钟在何处开始、在何处停止（从客户端调用到程序变量中的结果，如 Engineering Database Benchmark；或从收到请求到提交），因为每个点包含不同的组成部分。

**4c. 运行规则。** 规定到达稳态的预热、测量区间、冷与热协议（缓存如何清空，包括操作系统文件缓存，以及多少次迭代；Engineering Database Benchmark 报告第一次运行和渐近运行）、重复次数，以及一条可重复性判据（TPC-D：完整重跑在 5% 以内，报告较差的那次）。把两种变异来源分开：用来估计逐次运行噪声的重复，复用*同一*参数集；参数变化（步骤 3c）散布到各流上，或在它自己的敏感性运行中测量。若在每一次计时重复上都重新抽取参数，所报告的散布就成了噪声与负载变化的混合。然后规定各次运行之间已更新的数据怎么办（演化或重置）、超时，以及失败如何报告（规模点上的一次失败是一项结果，不要当成缺失值）。

**4d. 正确性。** 又快又错的答案不算结果。Sawyer 要求批处理作业报告可核验的数据（计数、合计），并做最低限度的错误检查，使所有系统执行相同的访问模式。规定每个操作的参考答案或校验和，以及有更新时的一致性测试（TPC 基准要求 ACID 测试）。把检查器本身检查一次：每个操作的一个故意写错的变体（差一的边界、错误的并列打破）必须通不过校验，否则这道门槛什么也证明不了。

**4e. 校准。** 证明瓶颈在被测系统。Sawyer 的方法：用回显替换该操作，以零思考时间提交，找出驱动端或网络达到饱和的速率，并把基准保持在远低于该速率之处。在运行期间监测驱动端自己的 CPU 和内存。

## 步骤 5 — 公平性、可移植性与披露

- **固定逻辑负载，给物理调优计价。** TPC-D 保持模式和查询固定（"SQL-as-written"，即按所写 SQL 执行；无 hint、无改写），并允许物理结构，但通过装载时间、更新成本和存储向它们收费。Set Query 走另一条路，强制规定索引。选定一种，并写下来。
- **对等的调优努力，事先固定。** 在第一次运行之前决定调优预算和重跑政策。Sawyer 的 "war of wizards"（巫师之战）是重跑不断升级，调优者越来越专业；Gray 把同一种动态描述为基准大战。基线得到的用心，与你所偏爱的系统相同。
- **测量的是系统，而不是实现者的聪明。** 若某一个实现里的技巧在其他实现里同样行得通，就在所有地方应用它，或者禁止它（Sawyer）。禁止依赖生成器人工痕迹的捷径（Engineering Database Benchmark 禁止根据连续的零件号推算磁盘地址）。
- **已发布的软件、标准设置、披露的偏离**（TPC 完全披露）。披露版本、配置、硬件、生成器种子、查询文本和查询计划；Ballinger 把不披露计划这一决定称为 TPC-D 的一个错误。
- **可移植性。** 用声明方式规定操作，让每个系统的适配层保持薄，并且避免只有一个系统才有的特性，除非该特性本身就是所问的问题。仍然为每个系统给实现者一个具体的起点：要使用的原生算子或表述、要紧的设置及其预定取值，以及已知限制。每一条这样的主张都标成「在钉定版本上核实」，而不是把它略去；一份没有系统细节的规范，会推动每个实现者以不同的方式把它重新发现一遍。

## 步骤 6 — 审计设计

1. **Gray 的四条准则**，每条都要有支持和反对的证据：*relevant*（该领域典型操作上的峰值性能与性价比）、*portable*（易于在许多系统上实现）、*scaleable*（适用于小型与大型系统）、*simple*（可理解，否则缺少可信度）。这些准则彼此冲突；点名冲突在何处。一份声称四条全部满足、又毫无张力的设计，是没有被检验过的。
2. **简单是一道门槛，不是一句坦白。** 若审计发现设计并不 simple，就在交付之前削减它。用 Cattell 的方法：丢掉其结果会跟着你所保留的度量走的那些度量，合并访问模式相同的操作（Sawyer 的网格），并把决策所不需要的一切移入被点名的扩展。核心基准应当扫描少数几个旋钮（那些可能改变排名的成本驱动因素），而不是你能够点名的每一种性质，并且一次完整的核心运行应当在目标硬件上放进一个工作日。每个扩展都陈述它回答的问题，因此它可以单独被排期，或单独被丢掉。削减的是实验和旋钮，绝不是使每一项被保留的结果可信的那些重复、正确性门槛或校准。
3. **Benchmarketing 检查。** Gray："For each system, there is some benchmark that rates that system the best."（对每个系统，都存在某个把该系统评为最佳的基准。）在研究中，作者既是厂商也是客户。要问：哪些操作或数据性质会让所偏爱的系统落败，它们是否以真实频率出现在负载里？所选的规模是不是它的优势达到峰值的地方？基线是否得到了对等的调优？结论在主成本驱动旋钮的一次扫描之后还能不能成立？把这次扫描加进实验矩阵。
4. **解释结果。** 一个没有机制的标题差异，会招来 Gray 所描述的那种怀疑。纳入一个把差异归因于机制的实验：一次消融（把关键技术关掉之后的系统）、按算子或按阶段的时间分解、对照代价模型的交叉核验（O'Neil 的 "multiple entry bookkeeping"，多笔记账），或者用差分测得的下限——DeWitt 把显示代价估计为两条在其他方面相同的 Wisconsin 查询之差；一条输入与输出相同的扫描并写出的查询，把该操作本身的代价分离出来。
5. **限度。** 列出本基准不会告诉你的事情。
6. **生命周期。** Ballinger 观察到，已发表的 TPC-D 配置在 "precision-tuning the overly-familiar"（精细调优那些过于熟悉的）查询集上。规划参数的随机化，以及对操作集的一次刷新。

## 步骤 7 — 交付

用 `references/spec-template.md` 把规范写到一个文件里（默认：项目中的 `benchmark/<short-name>-spec.md`，或用户指定的位置）。让它自洽：只看到这份规范的读者，就能够实现并运行该基准。让核心能够一次坐下来读完：把长的查询文本、生成器细节和分系统笔记放进附录。篇幅长并不等于严谨；若核心各节大约超过十页，就在交付之前削减。纳入基准自身的成本估计（Sawyer 的成本：人、机时、一次完整运行的墙钟时间）。若一次完整运行要花上数小时，就定义一个供迭代使用的缩减配置，以及爬升规模点的顺序。

对话里的回复要短：基准所服务的决策、主指标及其约束、规模规则、三个后果最大的权衡，以及尚未闭合的假设，并附上规范的链接。

把规范写精确：数字带单位，一个概念一个术语并在首次使用时定义，不使用不带数量的形容词；完整规则见本插件中的 `research-writing` 技能。运行基准并报告测得的结果，遵循本插件中的 `think-sharp` 技能；本技能写出的规范是那些步骤的输入（一个规模点对应其加倍阶梯的一级，一个失效点对应其 wall）。
